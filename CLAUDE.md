# Obsidian Mind Map View — Project Instructions

Mind mapping plugin for Obsidian that operates directly on `.md`
files with true bidirectional sync. Full plan: [obsidian-mindmap-plugin-plan.md](obsidian-mindmap-plugin-plan.md).
Performance rules (below) come from [performance-addendum-obsidian-mindmap-plugin.md](performance-addendum-obsidian-mindmap-plugin.md)
and **override any conflicting guidance in the plan.**

## Performance Rules (MANDATORY)

1. Performance is a top-priority requirement for this plugin. Treat it as a
   hard constraint, equal to correctness.
2. Before implementing any feature, consider its performance impact on large
   mind maps (1,000+ nodes). Prefer incremental/O(changed) approaches over
   full recomputation.
3. **Decision protocol:** Whenever you face a trade-off between performance
   and ANY other concern — feature richness, visual fidelity, code
   simplicity, development speed, memory usage, sync granularity, library
   convenience — you MUST STOP and ASK the user which to prioritize.
   Never silently choose. Present the options, the performance cost/benefit
   of each, and your recommendation, then wait for the user's decision.
4. Never introduce a dependency without stating its bundle-size and runtime
   cost and getting approval if it is non-trivial (> ~50 KB min+gzip or any
   per-frame overhead).
5. After implementing each milestone, run the performance benchmarks
   (`benchmarks.md`) and report the numbers against the budgets before
   moving on.
6. Avoid premature *micro*-optimization, but never make *architectural*
   choices that block later optimization (e.g., full re-render on every
   keystroke, full re-parse of the md file on every change).

Rule 3 is the most important one: **any performance-vs-anything trade-off
must be surfaced to the user as an explicit question, never decided
unilaterally.**

## Performance Budgets

| Metric | Target | Hard ceiling |
|---|---|---|
| Keystroke → node text update on screen | < 16 ms (1 frame) | 33 ms |
| Tab/Enter → new node visible & editable | < 50 ms | 100 ms |
| Fold/unfold branch (incl. rebalance animation start) | < 50 ms | 100 ms |
| Pan/zoom frame rate | 60 fps | 30 fps |
| Open a map with 500 nodes | < 300 ms | 700 ms |
| Open a map with 2,000 nodes | < 1 s | 2 s |
| Full relayout (auto-balance) of 2,000 nodes | < 100 ms compute | 250 ms |
| Markdown sync after node edit (write-back) | < 50 ms, debounced | — |
| Idle CPU usage (map open, no interaction) | ~0% | — |
| Memory for 2,000-node map | < 150 MB above baseline | 300 MB |
| Plugin bundle size | < 500 KB | 1 MB |

Benchmark fixtures: 100 / 500 / 2,000 / 5,000 nodes (generated by
`scripts/generate-fixtures.mjs` into `fixtures/`). 5,000 is a stress test —
degradation must be graceful, never a freeze.

## Architecture

Source lives in `src/`, one concern per directory. `Controller`,
`layoutEngine`, and `SvgRenderer` are the hot paths the performance rules
above bite hardest on — start there when reasoning about a perf trade-off.

- `model/` — the in-memory tree (source of truth; never re-derived from
  markdown per interaction): `types.ts`, `mutations.ts` (O(depth)
  subtree-count bumps), `commandStack.ts` (undo/redo via inverse closures
  capped at 100 edits, not full snapshots), `visibility.ts` (fold-aware
  visible-node list), `search.ts`, `links.ts`, `textWrap.ts`.
- `layout/` — `layoutEngine.ts` (d3-flextree wrapper, partial/per-region
  relayout), `sides.ts` (left/right branch assignment in anticlockwise
  document order, recomputed only on explicit Rebalance).
- `render/` — `SvgRenderer.ts` (hand-rolled SVG, dirty-tracked updates,
  viewport culling above a 300-node threshold), `colors.ts` (stable
  per-branch palette), `navigation.ts` (arrow-key nearest-node scan over
  cached layout positions).
- `sync/` — markdown ⟷ model, bidirectionally: `parser.ts`,
  `serializer.ts` (content-preserving — text the plugin doesn't understand
  round-trips untouched), `reconcile.ts` (structural-position matching
  after external file edits), `metadata.ts` (the `mindmap:` frontmatter
  block for fold state/manual positions), `debounce.ts` (400 ms write-back
  debounce), `goToSection.ts`, `parseExternalPaste.ts`.
- `controller/Controller.ts` — orchestrates mutations, selection, and
  clipboard across model/layout/render/sync; the central integration point.
- `view/` — Obsidian-facing UI: `MindMapView.ts` (the `TextFileView`
  implementation), `InlineEditor.ts`, `SearchPanel.ts`, `LinkModal.ts`.
- `settings/` — `PluginSettings.ts` (defaults/types), `SettingsTab.ts`.
- `main.ts` — plugin entry point; registers the view and commands.

## Project commands

- `npm run dev` — esbuild watch build, output goes to
  `dev-vault/.obsidian/plugins/mindmap-view/` for manual testing in Obsidian.
- `npm run build` — production build (minified, type-checked).
- `npm run fixtures` — (re)generate benchmark fixture `.md` files.
- `npm test` / `npm run test:watch` — Vitest unit tests (`test/`, one file
  per module area, mirroring the `src/` layout above).
- `npm run bench:m1` — parse+layout micro-benchmark.
- `npm run bench:m2` — mutate+relayout+render micro-benchmark
  (Tab/rename/delete/fold/unfold across the fixture sizes).
- `npm run bench:images` — image-heavy map benchmark (200 image-embed
  nodes — the worst case for the lazy-load/culling path).

## Process notes

- Feature and bug work follows [plans/MASTER-PLAN.md](plans/MASTER-PLAN.md):
  each backlog item gets its own subplan under `plans/` (root-cause
  analysis, steps, tests, perf impact) before implementation. Its
  "Per-item workflow" section is the checklist: re-read subplan → implement
  → `npm test` → benchmark if perf-relevant → manual dev-vault check → log
  the decision → update status.
- Log architectural decisions with performance implications in
  [DECISIONS.md](DECISIONS.md) (choice, alternatives, measured/estimated
  cost). It's a large, append-only log — search it rather than reading it
  in full, and add new dated entries instead of editing old ones.
- Log per-milestone benchmark numbers in [benchmarks.md](benchmarks.md).
- Obsidian is an Electron desktop app — there is no browser dev-server to
  preview. Verify UI changes manually in the dev vault; report this
  limitation instead of claiming automated visual verification.
- [SUBMISSION-CHECKLIST.md](SUBMISSION-CHECKLIST.md) tracks Obsidian
  community-plugin submission readiness (license, mobile verification)
  separately from the performance work above — check it before any
  release-related task. No GitHub Actions workflow is used for this
  project — releases/builds are done manually; don't (re)introduce a
  `.github/workflows/` CI/release pipeline.
